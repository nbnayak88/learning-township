## 1. The question this file answers

> *Integration architecture and event-driven design with SAP Advanced Event Mesh: when is an event the right answer, and how do you make it reliable?*

**What this file shows:** a six-event catalogue for OmniGrid, a rule for choosing API, event or batch, a delivery design (retention, replay, dead-message handling, reconciliation) and six evaluation scenarios.

**What it does not show:** a configured broker, a measured latency or a conformance result.

## 7. Choosing API, event or batch (new design)

| Use | When | Example from this case |
|---|---|---|
| API (request-reply) | The caller needs an answer now and the owner can serve it | Lookup of a current record |
| Event | Something happened that several consumers care about, and order or timing matters | grid/outage/reported/v1 |
| Batch | Large volume, no timing need, reconciliation or history load | Nightly reconciliation of acknowledgements |

## 8. Event catalogue (new design)

Topic convention: `ut/<domain>/<object>/<event>/v<version>` (the catalogue below shows the part after the root). Payloads carry an event id, a sequence or effective time, a schema version and a correlation id. Personal data is minimized (pseudonyms only).

| Topic | Producer | Consumers | Key fields | Why it matters |
|---|---|---|---|---|
| grid/outage/reported/v1 | Outage management | Field services, customer communications, planning | outage id, area, time, sequence | Start of coordination |
| grid/switching/performed/v1 (read-only copy) | Operations systems | Outage management, planning | switching id, area, time | Informational copy only; no command path |
| field/work-order/status-changed/v1 | Work management | Outage management, planning, customers | work order id, status, time | Conflicts with outage status |
| field/crew/location-updated/v1 | Crew application | Dispatch view | crew id, area, time | High volume; throttling |
| customer/notification/requested/v1 | Outage management | Customer communications | outage id, area, message class, time | Consent applies |
| ops/integration/dead-lettered/v1 | Integration platform | Integration operations, source owner | original event id, reason, attempts | No silent drop |

## 9. Delivery design (decisions to make, not stated values)

| Topic | Design | Value |
|---|---|---|
| Idempotency | Consumers recognize an event id already processed | Rule |
| Ordering | Sequence or effective time decides; late older events do not overwrite newer state | Rule |
| Retention and replay window | How long events can be replayed after an outage | To be decided |
| Redelivery and time to live | Broker settings per queue | To be decided; verify product support |
| Dead-message handling | Owner, review cadence and replay approval for failed events | Owner to be named |
| Acknowledgement and reconciliation | A consumer confirms; a periodic job compares sent and acknowledged | Rule |
| Schema versioning | Backward-compatible changes only inside a version; new version for breaking changes | Rule |
| Security | Topic-level authorization; no secrets or unneeded personal data in payloads | Rule |

## 10. Evaluation scenarios

| ID | Scenario | Expected behaviour |
|---|---|---|
| E1 | Outage and work-order events conflict on status | Reconciliation shows both and names the owner |
| E2 | A burst of crew location events | Throttled; latest only; no overload |
| E3 | The mesh is asked to carry a switching command | Refused; read-only copy only |
| E4 | Communications consumer offline in a storm | Events retained; replay on recovery; backlog visible |
| E5 | Duplicate outage reported events | Idempotent by outage id |
| E6 | Stale topology referenced by an outage event | Flagged; no connectivity claim |

## Three tabletop tests

A tabletop test is a paper walk-through, not a technical test of a running system.

| Test | Setup | Expected finding |
|---|---|---|
| T1 No command path | A consumer requests control through the mesh | Refused; security informed; design rule confirmed |
| T2 Storm backlog | Consumers lag during a storm | Backlog metrics visible; replay controlled; priority classes protect critical events |
| T3 Conflicting status | Outage and work-order events disagree | Conflict flagged with owners; no silent winner |
