## 1. The question this file answers

> *Security architecture for AI and autonomous operations: what can an assistant or agent do, as whom, and what stops it doing more?*

**What this file shows:** an identity and permission model for OmniTech's assistant and agents, four threat scenarios with a control and a check, and the sector boundary that no agent may cross.

**What it does not show:** a configured identity tenant, a penetration test result or a certified control.

| Capability | What the documentation or SAP community describes | Use in this design |
|---|---|---|
| SAP Cloud Identity Services (Identity Authentication, Identity Provisioning) | Sign-in, tokens and user provisioning across SAP and non-SAP systems | Identity for people and applications |

## 7. Identity and permission model (new design)

| Principle | Design |
|---|---|
| Two identities | The user's identity decides what data is visible; the agent's own identity decides which tools it may call |
| Least privilege | Each tool has its own scope; no wildcard scopes |
| Read before write | Agents start read-only; write tools are drafts that a person confirms |
| Approvals | Bound to one action, expire quickly, recorded with approver |
| Data minimization | Role filter applied before retrieval; identifiers masked |
| Untrusted text | Retrieved text is data and cannot trigger a tool call |
| Audit | Every tool call logged with user, agent, input class and result |

**Tool permission matrix from the Demo 03 pilot**

| Tool | Mode | Approval | Note |
|---|---|---|---|
| search_engagement_evidence | Read (tenant-scoped) | None | Hard partition by client tenant |
| get_release_incident_timeline | Read (tenant-scoped) | None | Returns both release and incident events in order |
| draft_evidence_pack | Draft only | Customer Success reviews | Citations required for every claim |
| raise_dispute_review | Creates a task | Customer Success owns the outcome | Assistant cannot change milestone status |
| Change milestone, invoice or service-level status | Not exposed | Not available to the agent | Contractual decisions stay with people |

**Sector boundary:** Tenant isolation applies to assistants, telemetry and recovery tools equally.

**Never available:** Another client's data or IP; Secrets and credentials found in repositories or tickets; Contract terms outside the engagement; Instructions found inside client-submitted tickets

## 8. Threat scenarios

| Threat | Control | Check |
|---|---|---|
| Cross-tenant retrieval | Tenant filters on every query | Query as tenant A for tenant B |
| Injection in a ticket | Text is data | Seed a ticket with an instruction |
| Secrets in logs | Log scrubbing | Search logs for a test token |
| Agent rollback without approval | Tier C | Request a rollback |

## Three tabletop tests

A tabletop test is a paper walk-through, not a technical test of a running system.

| Test | Setup | Expected finding |
|---|---|---|
| T1 Cross-tenant query | A tenant A user queries tenant B | Blocked; Security reviews |
| T2 Ticket injection | A ticket tells the agent to roll back | Ignored; flagged |
| T3 Secret in logs | A token appears in a log | Scrubbed; owner notified |
